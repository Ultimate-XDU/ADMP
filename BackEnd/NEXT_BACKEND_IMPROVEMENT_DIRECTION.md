# 后端下一步改进方向

生成时间：2026-05-16

- 剩余可入库文档已按 5 个一批完成处理，当前知识库状态为 `SYNCED=217`、`FAILED=5`。
- 大文件入库已停止，大于 20MB 的文件不进入本轮测试范围。
- 完整浏览器回归覆盖 60 个问题，最终只有 `C20` 被评估器标记；核对后该标记来自题库 `expected_doc_hint` 仍写“维修单位合格审定规则”，而实际有效证据来自已入库主文档“维修单位合格审定规定.pdf”。后端最终 sources 同时包含两个比较目标文档。
- 代表失败题 API 回归覆盖 `C20`、`K22`、`K23`、`C22`、`C23`、`C24`、`K15`，高亮一致性和跨文档来源覆盖均通过。

## 已落地的通用修复

1. 检索合同层

- 比较意图增加“异同”识别。
- 对显式《标题A》与《标题B》的比较题，优先收窄到引号内明确标题，降低短别名误扩展到相邻法规的概率。

2. 检索召回层

- 增加多目标文档覆盖补充召回。
- 对 comparison/multi-target 查询，缺失目标文档时尝试按目标文档过滤补召回，并对补召回结果走合同校验。

3. QA 证据选择层

- 在 prompt evidence selection 阶段保留多目标覆盖，避免第二目标文档被质量排序挤出最终 sources。
- 最终返回给前端的 sources 统一走展示高亮规整。
- `highlight_text` 只保留可在 `content` 或 `section_title` 中定位的短文本，避免把整页 PDF 上下文、页眉、日期和 AC 编号暴露给前端高亮。

4. 证据评分层

- 引入统一证据评分字段，区分展示分、排序分、RRF 分、rerank 分和结构化分，避免把不同量纲的 score 混用。

## 下一步优先级

1. 统一高亮生成入口

当前高亮仍分布在 PDF 切片、检索修复、QA 展示规整等多个位置。建议新增独立的 `evidence_display.py` 或等价模块，明确：

- `highlight_text`：前端可定位短高亮。
- `llm_context`：给生成模型使用的扩展上下文。
- `page_context`：用于证据页预览的页级上下文。

这样可以避免未来再次把模型上下文误当成前端高亮。

2. 多文档比较改为分桶排序

当前已保证 comparison 查询的最终 sources 覆盖多个目标，但排序仍是“先整体质量排序，再补目标覆盖”。下一步建议改为：

- 先按目标文档分桶。
- 每个显式目标文档至少选 1 条通过合同校验的证据。
- 桶内按 evidence quality 排序。
- 桶间按用户问题中的目标顺序输出。

这会让跨法规比较、同系列法规对比、FAA/CAAC 对照更加稳定。

3. PDF 解析清洗前移

英文 AC/FAA PDF 的页眉页脚、日期、页码、重复标题仍会进入部分 chunk。建议在解析阶段统一清洗：

- 页眉页脚识别：日期、AC 编号、Page/Par、重复章节头。
- 重复行压缩：同页或跨页重复超过阈值的短行降权或移除。
- 表格/列表结构保留：不要在清洗中破坏法规条款和编号层级。

4. 评估器产品化

本轮浏览器评估脚本只作为临时工具。后续建议转为后端可复用评估框架：

- 固定题库 schema：`question`、`expected_docs`、`expected_behavior`、`focus_terms`、`negative_docs`。
- 区分真实失败和题库元数据失败。
- 输出机器可读摘要，不依赖截图和临时浏览器脚本作为唯一判断。

5. 长期运行稳定性

- PDF 页面缓存增加文件 mtime 或 TTL 失效机制。
- 模型加载和 GPU 资源状态加入健康检查细分项。
- ES/Milvus 不可用时的错误分级保持清晰，避免前端误判为空答案。
